Rescue Mesh · The one node procedure · 8 August 2026

Reset Every Node
To The Same Known State

One procedure. It replaces five separate update runbooks, works whatever state a node is in, and is safe to run on a node that is already fine. About 10 minutes per node, once per node, and you are done.

Per node about 10 minutes Your data is not touched Safe to repeat yes, any number of times
check secrets→ git pull→ setup_node.sh→ reboot→ dtn_doctor→ next node
Why you need this. The three nodes have drifted apart. Each was updated at a different time by a different procedure, so DRONE_A is naming its adapter one way and DRONE_B another, and DRONE_S has not been touched this round at all. Both of A's and B's ways happen to work today, which is exactly why the difference is dangerous: it only surfaces later, when you swap an adapter or reboot mid-test.

Part one · Understand it first

01

What this does and does not touch

setup_node.sh is written to be re-runnable. Running it on a working node is a no-op in every way that matters. Running it on a confused node fixes it. That is why there is no longer any such thing as an "update runbook".

WhatHappens
Your databaseUntouched. Messages, personnel, announcements, everything stays
The fleet master secretUntouched. Read from deploy/secrets/, never regenerated. All your HMAC keys stay identical fleet-wide
Interface naming rulesRewritten to the current scheme
systemd unitsReinstalled and re-enabled
Helper scriptsReinstalled, including dtn-doctor
WiFi access point configRewritten
Firewall rulesReapplied for this node's role
Node TLS certificateReissued, signed by the same fleet CA
The reissued certificate is harmless. It is signed by the same fleet CA the apps already trust, so nothing needs reconfiguring. Any app with a live connection simply reconnects. You do not need to reload the CA in the GCC or on the phones.
02

The one command never to run

Do not run make_fleet_ca.sh

Not on DRONE_B, not on DRONE_S, not "just to be safe". It generates a NEW fleet master secret and a NEW certificate authority.

If you run it on one node, that node can no longer verify any record from the others, every issued credential stops working, sync rejects everything as forged, and the apps refuse the node's certificate. You would have to rebuild the whole fleet from that new secret.

It is run once, ever, on the operator laptop. The other nodes receive a COPY of deploy/secrets/. That has already been done for this fleet.

03

Before you start, on each node

The setup script refuses to run without the fleet secrets. Confirm they are present before you begin, so you do not discover it halfway through:

on the node
$ ls ~/rescue-mesh/deploy/secrets/

# You need at least these two:
#   fleet_secrets.env
#   fleet_ca.key   (and fleet_ca.crt)
If the folder is missing or empty
Do
Copy it from a node that HAS it, or from the operator laptop.
Do not
Generate a new one. See section 2.
copying secrets, example from DRONE_A
$ scp -r drone@10.99.0.1:~/rescue-mesh/deploy/secrets ~/rescue-mesh/deploy/

# Only works while the mesh is up. Otherwise use a USB stick, or copy
# from the operator laptop over the node's own WiFi.

Part two · The procedure

04

Run this on each node in turn

Identical on all three. The only thing that changes is the letter at the end: a, b or s. Do one node completely, verify it, then move on.

join that node's WiFi, then
$ ssh drone@10.42.0.1

$ cd ~/rescue-mesh
$ git pull

$ cd deploy
$ sudo ./setup_node.sh a          # a, b or s

$ sudo reboot
The adapter does not need to be plugged in. The script no longer requires it or its MAC address. A node whose adapter is currently in another node can still be set up completely.

After the reboot, log back in and check that node on its own:

on the node, after reboot
$ sudo dtn-doctor
What a correct node looks like
1. USB WiFi adapter present?          [OK] wlan1 exists
2. Is the adapter link stable?        [OK] no disconnects this boot
3. How is wlan1 given its name?       [OK] matched by DRIVER
4. Bring-up script installed?         [OK]
5. NetworkManager leaving it alone?   [OK] unmanaged
6. dtn-net service state?             active / enabled
7. Is wlan1 in IBSS mode?             [OK] type IBSS
8. Joined the RESCUE_DTN cell?        [OK] + address assigned
Line 3 is the one this whole exercise is about. It must say matched by DRIVER on every node. If any node still says matched by MAC ADDRESS, the setup script did not run successfully there: read its output again.
"No peers visible" is expected until at least two nodes have been through this and are powered at the same time. One node on its own can never show a peer, and the sync log will be empty for the same reason. Neither is a fault.

Now repeat the whole section for the next node. Do not start node two until node one shows a clean doctor result. Fixing one node at a time is much faster than discovering the same mistake three times.

05

Aux modules, once each

Separate from the Pi work and independent of it. DRONE_A and DRONE_B have aux modules; DRONE_S does not, so it needs nothing here.

From your laptop with the XIAO connected by USB-C:

laptop, repository root
$ git pull
$ cd firmware/aux1
$ pio run -t upload

# Then unplug, connect the second module, and run it again. The
# firmware is identical on both: node identity is stored on the
# board, not compiled in.

This carries the planned-shutdown notice, without which switching a node off makes the fleet report it as a failure. Details in the front panel runbook.

Part three · Confirming

06

Check the fleet agrees

Once at least two nodes are done and powered at the same time, from either of them:

on any node
$ curl -sk https://127.0.0.1:8443/health | grep -o '"node_id":"[^"]*"'

# Give it 15 seconds after the second node reaches IBSS: presence
# beacons go out every 10 s.

$ journalctl -u rescue-mesh-sync -n 40 --no-pager | grep table=
Expected
SYNC_OK | peer=DRONE_B | table=messages       | imported=0 | ...
SYNC_OK | peer=DRONE_B | table=personnel      | imported=0 | ...
        ... eight tables, ending with ...
SYNC_OK | peer=DRONE_B | table=lora_events    | imported=0 | ...
Eight tables is the number to count. imported=0 is correct when both nodes already agree. If you see fewer than eight, or SYNC_FAIL on any of them, the peer is on older code: run section 4 on that node.

The interchangeability test

Worth doing once, because it proves the naming fix and takes two minutes. Swap the adapters between two nodes, then on each:

on each node after the swap
$ iw dev wlan1 info      # type IBSS, on both, with nothing edited

If both nodes come back up with a working wlan1 and you changed no configuration anywhere, the fleet is consistent and adapters are now interchangeable. That is the end state this runbook exists to reach.

07

What "same state" means

After section 4 has been run on all three, every node has exactly this. Use it as a checklist if you suspect one has drifted again.

ThingIdentical on every nodeDiffers per node
Interface namingwlan0 by MAC, wlan1 by driverThe onboard MAC
Mesh cellSSID RESCUE_DTN, channel 6, BSSID 02:12:34:56:78:9aThe 10.99.0.x address
User access point5 GHz, 10.42.0.1SSID RESCUE_A / B / S
Fleet master secretYes, byte for byteNothing
Certificate authoritySame fleet CAEach node's own cert
Replicated tablesAll eight registeredTheir contents, until synced
ServicesSame set enabledMAVLink gateway on DRONE_S only
Aux moduleSame firmwareNone on DRONE_S
Different databases are not drift. Nodes are supposed to hold different records until they meet and sync. That is what a delay-tolerant network is. Only the CONFIGURATION has to match.

One node at a time, always. Most of the confusion in this project came from changing two things and then trying to work out which one broke. Finish and verify a node before touching the next.
