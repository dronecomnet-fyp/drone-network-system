Part one · The design problem

01

Why the switch must be two-pole

Read this before buying a switch. Getting it wrong does not damage anything, but it makes the system lie to you, which is worse.

How a node is powered

Each node is two independent computers with two independent batteries. This is deliberate and it is the core of the project's fault tolerance:

Sub-unitRuns onPowersRuntime
Main Compute UnitBattery A, 2S LiPo, via a buck converter to 5 VRaspberry Pi 4B and the USB WiFi adapterShorter
Auxiliary ModuleBattery B, 1S LiPo, direct to the XIAO boardESP32-C3, GPS, LoRa radio, battery monitorMuch longer, on purpose

The aux module outlives the Pi so that when the Pi dies, the aux module can still tell the rest of the fleet where the drone is over its long-range LoRa radio. That is the whole point of the design.

The fault in revision 1

The aux module works out whether the Pi is alive by listening for a heartbeat over the USB cable between them. No heartbeat for 15 seconds means the Pi has crashed.

Now put a single-pole switch in the Pi's supply only, and flip it:

what actually happens
  operator flips the switch
        ↓
  Pi loses power, heartbeat stops
        ↓
  aux module is STILL RUNNING on Battery B
        ↓
  15 s later: "the Pi has crashed"
        ↓
  starts transmitting LoRa fallback beacons
        ↓
  neighbouring drone hears them, logs them, replicates them
        ↓
  GCC shows: DRONE_A FAILED, Pi down, aux beaconing

  ...for a node somebody deliberately switched off.

Nothing breaks, but the fleet has been told a failure occurred, an operator gets an alarm, and someone may walk out to a drone that is simply turned off.

The fix, in two parts

  1. A DPST switch, cutting both batteries at once. DPST means Double Pole Single Throw: one lever operating two completely separate switches inside one body. Pole 1 cuts Battery A, pole 2 cuts Battery B, simultaneously. Both sub-units die together and the aux module never gets the chance to reach a wrong conclusion.
  2. A shutdown notice in software. Even with a DPST switch, the recommended way to power down is to shut the Pi down cleanly FIRST, then flip the switch, which protects the SD card. During those few seconds the Pi is halted while the aux module is still powered, which is the same trap again. So the Pi now sends the aux module a shutdown message just before it halts, and the aux module suppresses fallback for five minutes.
Why five minutes and not forever. A suppression flag that never expires means one stray message could silently disable the fallback beacon for the rest of a flight, and the beacon is the one thing this module exists to do. Five minutes covers a clean halt plus somebody walking over to the switch. After that the module goes back to normal behaviour, so a node accidentally left powered still reports itself.
If you already built a revision 1 panel

Replace the SPST switch with a DPST one and route Battery B's positive lead through the second pole. Nothing else changes on the panel. You also need the firmware reflash in stage 7. Until you do both, expect a spurious "node failed" alert every time you switch a node off; it clears itself after about two minutes.

02

What the panel does

LightStateMeaning
GreenblinkingBooting. Services have not answered yet
GreensolidNode is ready. Safe to walk away
Greenoff after a long bootServices failed to start. One long beep with it
AmbersolidThis node can see at least one other drone right now
AmberoffNo other drone visible. Normal sometimes, see below

Beeps: two short ones when the node first becomes ready, once. One long beep if it gives up waiting. Nothing after that, deliberately, because anything that beeps repeatedly gets muted or unplugged.

The amber lamp is the reason to build this. The network is delay-tolerant, so drones being briefly out of contact is normal. But a dead USB WiFi adapter looks exactly the same from the software side, and that failure has already cost this project an evening of debugging. With the lamp, you see it instantly from across a field.

Three ways to buy the wrong thing

An SPST switch. Three terminals instead of six. It only cuts one battery. This is the fault stage 1 exists to prevent.

A PASSIVE buzzer. Passive buzzers need a rapidly switching signal to make sound and will stay completely silent with this code. If the shop cannot tell you which it is: briefly touch it across a 3 V coin cell. Active buzzers beep. Passive ones click once.

A latching push button. The shutdown button must spring back when released. A latching one holds the line low and the Pi will shut down again the moment it boots.

Check the switch current rating covers the whole node. The Pi plus the USB WiFi adapter plus the aux module can pull well over 2 A in bursts, so 5 A gives sensible headroom. A small signal switch rated 0.5 A will overheat and eventually weld its contacts closed.
04

Resistors: why, and which value

Yes, you need them, one per LED. An LED is not a resistor. Connected straight across a voltage it draws as much current as the source will give, which destroys the LED, the GPIO pin, or both. The resistor is what sets the current.

The calculation, so you can adapt it if you use different LEDs:

Ohm's law for an LED
R = (V_supply - V_forward) / I_desired

  V_supply   = 3.3 V      Raspberry Pi GPIO output
  V_forward  = 2.0 V      typical green or amber LED drop
  I_desired  = 6 mA       bright enough, well inside limits

R = (3.3 - 2.0) / 0.006 = 217 ohm   ->  use the standard 220 ohm
ResistorCurrentVerdict
150 ohm8.7 mABrighter, still safe. Use if the lamps must be visible in direct sun
220 ohm5.9 mARecommended. Clearly visible in shade and indoors
330 ohm3.9 mAWorks, dimmer. Fine indoors, poor outdoors
noneuncontrolledDamages the LED and can damage the GPIO pin
Why not more current for a brighter lamp? A Raspberry Pi GPIO pin is rated for 16 mA, and 50 mA total across all pins. Two lamps at 6 mA plus a buzzer is comfortably inside that. Pushing each lamp to 15 mA would work but leaves no margin, and margin is what stops a marginal design failing in the heat.
The buzzer does not get a resistor. An active buzzer has its own driver circuit and expects the full 3.3 V. Adding a resistor makes it quiet or silent. Do check its datasheet current: if it draws more than about 25 mA it needs a transistor rather than a direct GPIO connection, though most small 3.3 V buzzers are well under that.

Pins 8 and 10 are marked do-not-use. That is GPIO14 and GPIO15, the serial port the system drone uses to talk to its flight controller. The four pins chosen above stay clear of it, so this exact panel works identically on all three nodes.
Which LED leg is positive? The longer leg. If the legs have been trimmed, look for a flat notch on the plastic rim: the flat side is negative. The resistor can go on either leg; it limits current the same way round.
06

Wiring: the power side

This is the part that stage 1 is about. Take your time and get it right.

A DPST switch has six terminals in two rows of three, or two isolated pairs. The two poles are electrically separate: they share only the lever. Pole 1 handles Battery A, pole 2 handles Battery B, and the two battery circuits must never touch each other.

both batteries through one lever
POLE 1  (Battery A, the bigger load)

  Battery A  (+) ────► switch pole 1 in
                       switch pole 1 out ────► buck converter IN+
  Battery A  (-) ──────────────────────────► buck converter IN-

  buck converter OUT (5 V) ──────────────────► Raspberry Pi power input


POLE 2  (Battery B, the aux module)

  Battery B  (+) ────► switch pole 2 in
                       switch pole 2 out ────► XIAO ESP32-C3  BAT+ pad
  Battery B  (-) ──────────────────────────► XIAO ESP32-C3  BAT- pad


  The two grounds stay separate. Do NOT bond them.
Do not join the two battery grounds

Keeping them separate is what makes the sub-units electrically independent, which is the fault-tolerance claim the whole design rests on. They are already linked for signal purposes through the USB cable between the Pi and the XIAO, and that is sufficient. Adding a second ground path creates a loop that can carry current between the packs.

Check the switch before you trust it

Multimeter on continuity mode, before anything is connected to batteries:

  1. Switch OFF. Every terminal should read open against every other terminal.
  2. Switch ON. You should find exactly two separate pairs that read continuous. If you find three terminals connected together, that is one pole of a DPDT with a common; use the common and one outer terminal per pole.
  3. Switch ON, then probe between pole 1 and pole 2. It must read open. If the two poles are connected, the switch is not DPST and you have bridged your two batteries.
Do that third check. It is the one that catches a mislabelled switch, and bridging a 2S pack to a 1S pack will damage the 1S cell.

Part three · Software

07

Reflash the aux module

The shutdown notice from stage 1 needs the current firmware on the aux module. Do this for both aux modules (DRONE_A and DRONE_B). DRONE_S has no aux module and needs nothing here.

This runs from a laptop with PlatformIO installed, with the XIAO connected by USB-C.

laptop, repository root
$ git pull
$ cd firmware/aux1
$ pio run -t upload

# Repeat with the second module plugged in. The firmware is IDENTICAL
# on both; the node identity is stored on the board, not compiled in,
# so there is nothing to change between the two uploads.
Confirm it took
pio device monitor
You should see JSON lines with gps and battery types. Press Ctrl+C to exit. If the port is busy, unplug the module from the Pi first: only one program can hold the serial port.
Without this reflash the panel still works. You just get one spurious "node failed" alert each time you switch a node off cleanly, and it clears itself after about two minutes. Reflashing removes it entirely.
08

Enable it on the Pi

Do this on each node that has a panel fitted. Connect to the node's WiFi first; every node answers on 10.42.0.1 from a device joined to it.

on the node
$ ssh drone@10.42.0.1
$ cd ~/rescue-mesh
$ git pull

# Open this node's config. Use drone_b.conf or drone_s.conf as appropriate.
$ nano deploy/nodes/drone_a.conf

# Find this line and change false to true:
#     INDICATOR=false     ->     INDICATOR=true
# Ctrl+O to save, Enter, Ctrl+X to exit nano.

$ cd deploy
$ sudo ./setup_node.sh a        # use b or s for the other nodes

Then enable the shutdown button, which is a separate one-line change:

on the node
$ sudo nano /boot/firmware/config.txt

# Add this line at the end of the file:
dtoverlay=gpio-shutdown,gpio_pin=3,active_low=1,gpio_pull=up

$ sudo reboot
Expected after the reboot
green lamp blinks while booting, then goes solid
two short beeps
amber lamp lights if another drone is currently in range
The setup script installs the python3-gpiozero library automatically when INDICATOR is true, so there is no separate install step.
09

How to switch a node off

Two ways. Use the first one.

Correct: clean shutdown, then switch
1
Press and release the panel button.
2
Wait for the green lamp to go out. Usually 10 to 20 seconds.
3
Flip the DPST switch to OFF.

Behind the scenes, step 1 makes the Pi tell the aux module the shutdown is planned, so no fallback alert is raised. Step 2 lets the filesystem finish writing, which is what protects the SD card. Step 3 cuts both batteries together.

Acceptable in a hurry: switch only
1
Flip the DPST switch to OFF.

Both sub-units die at the same instant, so no false alert is raised. The cost is an unclean filesystem shutdown, which is survivable occasionally and corrupts the SD card eventually if you make a habit of it.

Never do this

Do not cut only Battery A, and do not unplug only the Pi while the aux module runs, unless you are deliberately testing the fallback behaviour. That is precisely the condition that generates a genuine failure alert, which is correct: from the fleet's point of view a Pi with no power IS a failed Pi.

Turning it back on: flip the switch to ON. If the Pi was halted with the button but power was left on, press the same button to wake it.

10

Test it

Five tests, in order. The last two are the ones that prove the revision 2 fix works.

  1. Lamps and beep. sudo systemctl restart rescue-mesh-indicator. Expect blink, solid green, two beeps.
  2. Amber tracks the mesh. With two nodes up, both amber lamps should be lit. Unplug the USB WiFi adapter from one; both should go out within about 10 seconds. Plug it back in and they should return. This is the test worth doing properly, because it is the exact field failure the lamp exists to reveal.
  3. Clean shutdown. Press the button. Green should go out within about 20 seconds and the Pi should stop responding to ping.
  4. No false alarm on a clean shutdown. With a second node running and a GCC connected to it, do a clean shutdown on the first node. Watch the GCC's Degraded tab for two minutes. It must stay empty. If a degraded entry appears, the aux module did not get the shutdown notice: check that stage 7's reflash was done on that module.
  5. Real failures still alarm. Now pull power from the Pi ONLY, leaving the aux module running. Within about a minute the GCC should show that node as degraded. This confirms that suppressing the planned case did not break the genuine one.
Tests 4 and 5 are a pair and both are needed. Test 4 alone would also pass if you had accidentally disabled fallback altogether, which would silently remove the project's main fault-tolerance feature. Test 5 is what rules that out.

12

What it cannot do

The panel runs on the Raspberry Pi, so it cannot show anything once the Pi is dead, which is exactly the fallback case. A genuinely failed node goes dark locally.

The aux module still reports the failure to the rest of the fleet over LoRa, so the GCC sees it and a neighbouring drone logs every beacon. But nobody standing next to the failed drone learns anything from looking at it.

This was accepted deliberately rather than overlooked. Moving the lamps to the aux module, which does survive the Pi, would mean freeing a pin on the XIAO, and every signal pin is already allocated. It would cost a LoRa line or need an I2C expander, which is a project rather than an afternoon.
