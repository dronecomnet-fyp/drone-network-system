Power Switch, Beep
and Status Lamps

What to buy, exactly where to solder it, and what each light means. The software is already written and shipped; this is the hardware half. About 40 minutes per node with a soldering iron.

Per node cost under 500 LKR Pins used 4 of 40, all free Code already on the node Risk read stage 4 first
buy parts→ solder 3 pins + GND→ switch in the supply lead→ INDICATOR=true→ two beeps and a green lamp
The amber lamp is the reason to build this. It is lit whenever the node can currently see at least one peer. The failure that took two nodes out during testing, a USB Wi-Fi adapter browning out and dropping off the bus, shows up here instantly as an unlit amber lamp. Without it, that failure is only visible by reading sync logs, which is how it cost an evening.

Part one · The design

01

What it does, and why it is on the Pi

Three things: a physical power switch for the whole node, a beep when the node becomes ready, and two lamps that tell you the node's state from across a field without opening a laptop.

LightStateMeaning
GreenblinkingBooting. Services have not answered yet
GreensolidNode is ready. Safe to walk away
Greenoff after a long bootServices failed to start. One long beep accompanies this
AmbersolidThis node can see at least one peer right now
AmberoffNo peers visible. Normal in a DTN, or a dead radio

Beeps: two short ones when the node first becomes ready, once. One long beep if it gives up waiting. Nothing after that, deliberately, because anything that beeps repeatedly gets muted or unplugged.

Why the Pi and not the aux module. The aux module was the first instinct, since it survives the Pi dying and could therefore beep during LoRa fallback. It is not possible: every XIAO ESP32-C3 signal pin is already allocated (CHANGES item 10, where LoRa MISO had to move to the last spare). Adding a buzzer would mean giving up a LoRa line. The operator also chose the Pi independently.

Check the buzzer current. Anything drawing over roughly 25 mA needs a transistor rather than a direct GPIO connection. Most small 3.3 V active buzzers are well under that, but read the datasheet before wiring it straight to a pin.

Pins 8 and 10 are marked do-not-use for a reason. That is GPIO14/15, the UART DRONE_S uses for its flight controller. It is the only GPIO peripheral in the whole design, and the four pins above are chosen to stay clear of it, so this panel is identical on all three nodes.

The LED long leg is the positive one. The resistor can sit on either side of the LED; it limits current the same either way. If a lamp never lights, this is the first thing to check.
04

The switch, and the thing that will bite you

Wire the switch in series with the positive supply lead feeding the Pi, before the Pi's power input. It carries the full node current, which is why the 5 A rating matters.

Read this before fitting a bare power switch

Cutting power to a running Pi is an unclean shutdown. Do it repeatedly and the SD card will eventually corrupt. That is not theoretical here: these nodes already lose power in the field, and one has already been taken down by a USB brownout.

Two ways to live with it, in order of preference:

  1. Fit the optional button on GPIO3. Press it to shut down cleanly, wait for the green lamp to go out, then flip the switch. GPIO3 is special: the same button also WAKES a halted Pi, so one button does both jobs. Enable it by adding one line to /boot/firmware/config.txt:
    /boot/firmware/config.txt
    dtoverlay=gpio-shutdown,gpio_pin=3,active_low=1,gpio_pull=up
  2. Accept the risk and keep a spare flashed SD card in the kit. Reasonable for a demo, poor for a deployment.

Part three · Software and testing

05

Turn it on in software

The code is already on the node. Every node conf now ships with the switch present and set to false, so you are changing one word.

on the node
$ cd ~/rescue-mesh
$ git pull

# Edit this node's conf: deploy/nodes/drone_a.conf (or _b, or _s)
# Change INDICATOR=false to INDICATOR=true
$ nano deploy/nodes/drone_a.conf

$ cd deploy
$ sudo ./setup_node.sh a          # or b, or s
$ sudo systemctl status rescue-mesh-indicator
The setup script installs python3-gpiozero for you when INDICATOR is true, so there is no separate apt step to forget. It only installs it on nodes that ask for it, since a node with no panel fitted has no use for the library.
06

Test it

You do not need to reboot to test. Restarting the service replays the whole startup sequence.

on the node
$ sudo systemctl restart rescue-mesh-indicator
Expected, within a few seconds
green lamp blinks, then goes solid
two short beeps
amber lamp lights IF another node is currently in range
Amber staying dark is not a failure on its own. With one node powered there is nothing to see. Power a second node and it should light within about 10 seconds, which is also the cleanest proof the mesh is up.
The one test worth doing properly

With two nodes up and both amber lamps lit, unplug the USB Wi-Fi adapter from one of them. Both amber lamps should go out within about 10 seconds. That is the exact field failure this panel exists to make visible, and confirming it now means you will recognise it instantly later.

08

What it cannot do, stated plainly

The panel runs on the Raspberry Pi. It therefore cannot indicate anything once the Pi is dead, which is exactly the LoRa fallback case: a failed node goes dark locally.

The aux module still reports that condition to the rest of the fleet over LoRa, so the GCC's Degraded tab sees it and a neighbouring drone logs every beacon. But nobody standing next to the failed drone will know from looking at it. This was accepted deliberately rather than overlooked, and it is the direct cost of the pin shortage on the aux side.

If you ever want local indication of a dead Pi, it has to move to the aux module, which means freeing a XIAO pin, which means giving up a LoRa line or adding an I2C GPIO expander. That is a real project, not an afternoon, and it is recorded as future work rather than a gap.
