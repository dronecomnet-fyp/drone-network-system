Rescue Mesh · Field backlog rollout · 5 August 2026

Update Every Node
for the LoRa Log

Eighteen tester findings are fixed. Two of them need new code on the drones: the LoRa event log that feeds the new Degraded tab, and the option list the emergency app now reads from the node instead of carrying its own copy. Roughly six minutes per node.

Nodes DRONE_A, DRONE_B, DRONE_S Database new table, created automatically Firmware no reflash needed Downtime about 10 s per node
git pull→ restart 3 services→ check the new table→ check the options endpoint→ repeat on B and S
Do the nodes before the phones. The emergency app now asks the node which SOS options to show. Against a node running the old code that request fails, the app quietly falls back to its built-in list, and you will be testing the fallback path without knowing it. Nothing breaks, but nothing proves anything either.

Part one · Context

01

What actually changed on the drones

Only two things reach the Raspberry Pi. Everything else in this round was app-side.

ChangeWhy it existsWhat it touches
lora_events table Every LoRa frame a node hears is now logged, not just folded into the health snapshot. The Degraded tab reads it to answer what a downed drone has been telling you, how strong the signal is, and what message it was still carrying. New table, new /lora-events and /sync/lora-events routes, the aux bridge writes to it
/portal-options The emergency app now shows the same tappable options as the captive portal, fetched from the node, so a victim with the app and a victim with a browser report the same things. One read-only route on the public plane
The table replicates, unlike node health. The node that hears a beacon is whichever one is nearest the failure, and you may be joined to a different one. That is also why all three nodes need updating rather than just the one you usually sit on: a node running old code has no /sync/lora-events to pull from, so the log stops at whoever heard it.
No firmware, no wiring, no SD card work. The aux modules are unchanged in this round. If you have not yet reflashed them for the phantom Battery B fix from the last round, do that separately; it is not part of this.

Part two · The node update

02

Pull and restart, on each node in turn

Join that drone's Wi-Fi, then SSH in. The node's own address is always 10.42.0.1 from a phone or laptop joined to it.

DRONE_A, then B, then S
$ ssh drone@10.42.0.1
$ cd ~/rescue-mesh
$ git pull

# The API creates the new table on start. The sync daemon needs the
# restart to learn the new table exists; the aux bridge needs it to
# start writing log rows.
$ sudo systemctl restart rescue-mesh-api rescue-mesh-sync rescue-mesh-auxbridge
Nothing to migrate by hand. Table creation runs at service start and uses CREATE TABLE IF NOT EXISTS, so existing messages, personnel and checkins are untouched. No SQL, no data loss, and running this twice is harmless.
03

Gate: the new table exists

Ask the node's own health endpoint rather than the database, because that is the same answer the GCC will get.

on the node
$ curl -sk https://127.0.0.1:8443/health | grep -o lora_events
Expected
lora_events
One line of output is a pass. It means the table exists and the health endpoint is counting it.
Stop if empty

No output means the API is running old code. Check git log -1 is the commit you expect, then systemctl status rescue-mesh-api for a start failure. Do not continue to the next node: you want one node right before you repeat a mistake three times.

04

Gate: the node serves its option list

This is the endpoint the emergency app now reads. It lives on the public plane, port 80, with no authentication, exactly like the captive portal it mirrors.

on the node
$ curl -s http://127.0.0.1/portal-options
Expected
{"config_id":"stock","headline":"Tap what you need. You can tap more than one.","situations":[{"id":"trapped",...
"config_id":"stock" is correct on a node you have never pushed mission options to. If you have pushed some, you will see your own labels and a 12-character id instead. Either is a pass; an HTML page instead of JSON is not.
Urgent options come first in that list. The node sorts them, and the app renders in the order it is given, because somebody skimming in an emergency reads the top and may never reach the bottom.
05

Gate: the log replicates between nodes

Run this after at least two nodes are updated and can see each other. Watch one sync cycle go by; the default interval is 30 seconds.

on the node
$ journalctl -u rescue-mesh-sync -n 40 --no-pager | grep lora_events
Expected
SYNC_OK | peer=DRONE_B | table=lora_events | imported=0 | updated=0 | rejected=0
imported=0 is right when nothing has gone wrong yet: there are no LoRa events to replicate until a drone actually drops to fallback. What matters is that the line appears at all, which proves both ends know about the table.
Stop if there are no SYNC lines at all

That is not a problem with this update. It means this node cannot see any peer, and the first thing to check is whether the interface still exists at all: iw dev wlan1 info. A missing interface is what took two nodes out during testing, and it looks exactly like a sync bug from up here.

Part three · The laptop and the phones

06

Rebuild the GCC on Windows

Most of this round landed in the GCC: a Degraded tab, map layer filters, the @ attach picker, GCC placement and intent drawing, and the reordered Mission tab.

PowerShell, repo root
PS> git pull
PS> cd gcc_app
PS> flutter build windows --release
New in the GCC
Degraded tab
Downed drones, what they beaconed, signal strength, the message they were carrying, and a filterable LoRa log. Nodes that recovered stay listed for an hour.
Layers button
Bottom right of the map. Counts hidden layers rather than visible ones, so a filter you forgot is on stays visible.
@ in a message
Attaches a drone, victim or rescuer with its coordinates.
Place GCC / Advance / Suspect
On the map panel in planning mode. All three feed the AI advisor.
Mission tab order
Area first, then resources, then the plan. Drag a spare module chip onto a drone card to attach it.
An unapproved AI plan no longer appears on the operations map. It shows while you are in planning mode, blinking, and nowhere else until you approve it. If you go looking for a draft on the main map and it is not there, that is the new behaviour working.
07

Reinstall the two phone apps

Both changed. Install over the top; nothing needs uninstalling first.

What is different
Rescue app
Sign in by scanning the QR the GCC shows when credentials are issued. No typing, and it works on a drone that has never heard of that person. The PIN screen is still there as the fallback.
Emergency app
The SOS screen now offers the same tappable options as the captive portal, fetched from the node. Location is shared by default with a switch to opt out.
The rescue app will ask for camera permission the first time you scan. It is marked optional, so a phone with a broken camera still installs and falls back to the PIN.

Part four · Proving it

08

Prove it end to end

Four checks. The first three take a minute; the fourth is the one worth doing properly.

  1. Options match. Open the emergency app on a drone Wi-Fi and open http://10.42.0.1/ in a browser on the same network. The two lists of buttons must be identical. If the app shows different wording, it fell back to its built-in list and the node did not answer.
  2. Scan sign-in. Issue credentials in the GCC, scan the QR with the rescue app. You should be signed in with no typing. Then do it again on a DIFFERENT drone that has not synced yet, which is the whole point of the change.
  3. Layers and drafts. In the GCC, run the AI advisor if you have a key set, and confirm the draft blinks in planning mode and disappears from the map when you leave planning mode.
  4. A real fallback. Pull power from one drone's Raspberry Pi while leaving its aux module powered. Within about a minute the Degraded tab on a GCC joined to ANOTHER node should show that drone, with a beacon age, a signal strength and the last message it was carrying, and its map marker should blink. Restore power and it moves to Recovered after the module sees three consecutive pings.
Power warning, from the last round

Do this test on a mains supply or a phone charger, not the battery pack. The battery arrangement as tested cannot reliably power a Pi plus the USB Wi-Fi adapter plus the aux module: the adapter browns out and silently drops off the bus, and you will spend the evening debugging sync instead of testing fallback.

09

If something is wrong

SymptomWhat it meansDo this
Degraded tab is empty during a real fallback The GCC is joined to a node that cannot hear the beacon, and the node that CAN hear it has not synced yet Wait one sync cycle, then check journalctl -u rescue-mesh-auxbridge -n 30 on the node nearest the downed drone for FALLBACK_BEACON lines
LORA_EVENT_LOG_FAIL in the aux bridge log The log write failed, deliberately without taking the bridge down with it Check the API restarted and the table exists (stage 03). The bridge keeps working either way; only the log is affected
Emergency app shows different options from the browser The node did not answer /portal-options, so the app used its built-in list Re-run stage 04 on that specific node. It is almost always a node that was missed
Scan sign-in fails with "not a rescue sign-in code" The QR is not one of ours, or the GCC that issued it is older than this build Reissue the credentials from the rebuilt GCC and scan the new code
Log grows large after a long incident Expected. A node down for a day beacons about 2900 times and every node in earshot keeps a copy Nothing. Pruning to 2000 rows runs by itself every twentieth sync cycle, roughly every ten minutes
Rolling back is a git checkout away. The new table is additive, so an older build simply ignores it. Nothing in this round changes an existing table's shape, and no data written by the old code becomes unreadable.
