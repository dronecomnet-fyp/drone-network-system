Testing Session Plan
and Evidence Capture List

Every measurement to take and every image to capture for the Testing and Results chapter, in the order they have to happen. Forty-four numbered items. Work down the list and you finish with a complete chapter's worth of evidence and nothing to re-shoot.

Total time about 2 days, split into 6 sessions People 2 (3 for the field session) Output 44 evidence files + 9 filled tables
0 prepare→ 1 test suites→ 2 screenshots→ 3 bench→ 4 field→ 5 endurance→ 6 the recording
Written for two USB WiFi adapters, not three. The fleet has three nodes but only two AR9271 adapters, so at most two nodes can be on the mesh at any moment. Section E works through exactly which tests that affects, which is fewer than it sounds: only two of the forty-four items need a swap, and one of them arguably becomes a BETTER test because of it. Read section E before session 3.
The order is not arbitrary. Screenshots come after seeding, because a figure captioned "the victim message feed" showing an empty list proves nothing. The Degraded tab can only be photographed while a node is actually degraded, so it sits inside the fallback measurement rather than in the screenshot session. Field range work needs the battery question settled first, because a range test on a browning-out adapter measures the wrong thing entirely.

Part A · Before anything

A

Rules and naming

Five rules. Breaking any of them means re-shooting later, which is the one thing this plan exists to prevent.

  1. One naming scheme. EV-NN-short-name.png, matching the ID in this document. EV-14-gcc-degraded-tab.png. Your teammate can then drop a figure into the report without asking which file is which.
  2. Log every capture as you take it. The log sheet is below. Date, evidence ID, node ids, git commit, power source. A screenshot with no recorded conditions is an illustration; with them it is evidence.
  3. Never real personal data. Demo names, demo device ids, invented message text. If a real phone number or name appears in a frame, that image cannot go in the report.
  4. Consistent capture settings. GCC window at 1600 x 1000 for every screenshot. Same theme throughout, do not mix light and dark. Phone screenshots in the same orientation.
  5. Three trials minimum for anything with a number attached. Report all three and the median. One measurement is an anecdote.

02

Seed and screenshots, 2 hours

Eighteen images. This is the session that fixes the report's biggest presentational weakness: it currently has no UI screenshots at all.

2a. Seed the data first

Join the laptop to DRONE_A's Wi-Fi, then:

laptop, on RESCUE_A
$ python3 tools/seed_demo_data.py

# About 2.5 minutes. It paces itself to 13 s between writes because
# the victim plane rate-limits to 5 per minute per IP. That pause is
# the limiter working, not the script hanging.

Then, by hand in the GCC, because these are not public-plane records:

  1. Log in as HQ. Issue three personnel credentials with realistic role names.
  2. Post two announcements, one NORMAL and one URGENT.
  3. Create a mission: name it, pick a disaster type, add two or three challenges.
  4. Draw the operation area over ground your MBTiles file actually covers.
  5. Add four drones: two by unit id, one volunteer with a module attached, one minimal. Add two spare modules.
  6. Place the GCC, draw two advance arrows with notes, circle one suspected area.
  7. Add four placements with different roles, so the map has coverage circles.
  8. Sign a rescuer in on the second phone and let it report location for a few minutes, so rescuer pins appear.
Do this seeding once and screenshot everything in one sitting. Data ages: every screen shows a data age, and a set of figures where one says "3s" and another says "47m" looks careless.

03

Bench measurements, 2.5 hours

Four measurements and eight captures, all indoors with nodes on mains. These are the numbers the report has none of.

3a. Sync convergence (measurement M3)

The headline DTN number. Three nodes in range, GCC watching.

on DRONE_B, watching for A's message
$ while true; do \
    printf "%s %s\n" "$(date +%T)" \
    "$(curl -sk https://127.0.0.1:8443/health | grep -o '\"messages\":[0-9]*')"; \
    sleep 1; done
  1. Submit a message on DRONE_A through the captive portal. Note the second.
  2. Watch the count increase on B. Note the second. That difference is one hop.
  3. Twenty trials. It is quick and the spread is the interesting part.
  4. For the two-hop case, use the store-and-forward procedure in section E. It needs an adapter swap and takes about ten minutes per trial, so do five, not twenty.
EV-25: photograph this terminal mid-run
| Trial | A to B (s) | A to S (s) | Two-hop via S (s) |
|-------|-----------|-----------|-------------------|
| 1     |           |           |                   |
| ...   |           |           |                   |
| median|           |           |                   |
Predicted: median near 15 s, worst case near 30 s, because SYNC_INTERVAL is 30 s and submissions land uniformly within a cycle. If your median lands near 15, say so explicitly in the report: it shows the mechanism behaves as modelled rather than by luck.

3b. Fallback and recovery (measurement M4)

The single most valuable sequence in the session, because it exercises the aux module, LoRa, the log, replication and the GCC in one event. Five trials.

  1. Adapters in A and S. GCC joined to S. DRONE_B is the victim of the test and needs no adapter at all, because its Pi will be off. See section E: this is the test the two-adapter limit actually improves.
  2. Start a stopwatch and pull power from B's Raspberry Pi only, leaving its aux module powered.
  3. Record: aux enters fallback, A logs FALLBACK_BEACON, GCC shows B degraded, Degraded tab shows the carried message.
  4. Restore power. Record time until B returns to NORMAL and leaves the degraded list.

The report currently describes the OLD one-way behaviour as a deliberate choice. This image is the evidence for the correction.

3c. Battery monitor accuracy (measurement M8)

  1. Multimeter on Battery A terminals. Compare against the voltage in /health. Five points across a discharge.
  2. Same for Battery B.

That is field backlog #8 and it is worth a paragraph either way: an unconnected INA3221 input floats near the supply rail and cannot be told from a full cell by voltage alone.

Three range measurements. Pick a day with no rain and record the weather, because range figures are site and condition specific and the report has to say so.

05

Endurance, overnight

Two long runs. Start them at the end of a day and read the results the next morning. This is the measurement that tests the report's power chapter, which is currently calculated and never verified.

5a. Battery A, on the pack (measurement M7)

Node fully assembled, all services, a phone connected to the AP, syncing with a peer. Log every 60 seconds until it dies.

on the node under test
$ while true; do \
    printf "%s %s wlan1=%s\n" "$(date +%T)" \
    "$(curl -sk https://127.0.0.1:8443/health | grep -o '\"a_v\":[0-9.]*')" \
    "$(iw dev wlan1 info >/dev/null 2>&1 && echo up || echo GONE)"; \
    sleep 60; done | tee ~/batt_a_run.log
The wlan1 column is the whole point. If it reads GONE partway through, you have not measured runtime, you have measured time-to-brownout, and that is a different and more important result. Report it as such.

EV-41: the log file itself, plus a plot of voltage against time.

Compare against the calculation, do not replace it
| Figure                             | Calculated | Measured | Difference |
|------------------------------------|------------|----------|------------|
| Battery A, 2S 2500 mAh prototype   | 1 h 49 m   |          |            |
| Battery B fallback, 1S 1500 mAh    | 8 h 51 m   |          |            |
Keeping both columns is the honest presentation. A calculation that turns out optimistic is a finding, not an embarrassment.

5b. Battery B in fallback

EV-42: Pi off, aux module in fallback, beaconing until it dies. Have a second node log every beacon it hears, so the death time is recorded automatically in lora_events without anybody staying awake.

This one run validates the entire dual-battery argument, which is one of the project's main design claims. Worth the night.

EV-43: repeat 5a on a 3 A supply, at least for two hours, to show the node stays healthy when power is adequate. Together with 5a this makes the power finding concrete rather than anecdotal.

06

The one continuous recording, 1 hour

EV-44. A single unedited screen recording of the whole pipeline, victim to rescuer, with no cuts. One take. It is the strongest single piece of evidence in the project because it crosses more independently built components than anything else, and a cut in the middle destroys exactly that.

  1. Locked phone. Emergency app armed. Walk into range of a node.
  2. Notification appears. Tap it, join the Wi-Fi.
  3. Tap two SOS options, leave location on, send.
  4. Cut to the GCC: the SOS appears on the map and in Live Ops.
  5. Second phone, rescuer: scan the QR from the GCC to sign in, no typing.
  6. Rescuer claims the message. Rescuer replies.
  7. Back to the victim phone: the reply arrives in the conversation screen.
Rehearse it once before recording. The failure mode is fumbling a step and restarting, and by the fourth attempt the data is stale and the ages on screen look wrong. One rehearsal, then one take.
Also record what does NOT work

If a step needs two attempts, keep that in the take and say so. A recording where everything is flawless first time invites the question of how many takes it needed. One visible retry, acknowledged, is more credible than a perfect run.

E1. Do this first: make the adapters interchangeable

Skip this and you will lose an afternoon

Each node pins its adapter to the name wlan1 by MAC address. Move an adapter to a different node and it comes up under a kernel-assigned name instead. The mesh service then finds no wlan1, the cell never forms, and from the laptop this looks exactly like a sync bug. That failure has already cost this project an evening once.

The fix is one edit per node. Get both adapter MAC addresses first: plug each into any node in turn and run ip link, or read cat /sys/class/net/wlan1/address.

on EACH of the three nodes
$ ssh drone@10.42.0.1
$ cd ~/rescue-mesh
$ git pull
$ nano deploy/nodes/drone_a.conf     # or _b, or _s

# Set BOTH lines to the two adapter MACs. Same two values on all
# three nodes: whichever adapter is plugged in becomes wlan1.
DTN_MAC=00:c0:ca:aa:bb:cc
DTN_MAC_ALT=00:c0:ca:dd:ee:ff

$ cd deploy && sudo ./setup_node.sh a    # or b, or s
$ sudo reboot
Confirm on each node, with either adapter plugged in
iw dev wlan1 info
It must print interface details. If it says "No such device", the MAC in the conf does not match the adapter you have plugged in. Fix that before going any further; every measurement after this point depends on it.

E2. The swap procedure

  1. Shut the source node down cleanly (panel button, wait for green out, or sudo poweroff).
  2. Unplug the adapter and plug it into the destination node.
  3. Power the destination node up.
  4. Run iw dev wlan1 info before doing anything else. Every time. It takes two seconds and it is the check that stops you measuring nothing.
Do not hot-swap into a running node. The interface naming is applied at boot, so an adapter plugged into a running Pi may come up under the wrong name even with E1 done.

E3. Two-hop convergence, the better version

Three nodes in one room is a poor test of a delay-tolerant network anyway, because nothing ever has to be carried. With two adapters you are forced into a test that is closer to the real thing: A and B never meet, and the message still arrives.

one trial, about 10 minutes
1.  Adapters in A and S. B has none and is powered off.
2.  Submit a message on A through the captive portal. Note the time.
3.  Wait for it to reach S (watch S's health count). Note the time.
        that is hop 1

4.  Cleanly shut down A. Move A's adapter to B. Power B up.
        A is now off. A and B have never been on the mesh together.

5.  Confirm on B:  iw dev wlan1 info
6.  Wait for the message to reach B from S. Note the time.
        that is hop 2

7.  Verify on B that the message content and its ORIGIN NODE are intact.
EV-25b: record this table, five trials
| Trial | Hop 1 A to S (s) | Carry gap (mm:ss) | Hop 2 S to B (s) | Origin preserved |
|-------|------------------|-------------------|------------------|------------------|
| 1     |                  |                   |                  |                  |
The "origin preserved" column is the important one. It shows the record still names A as its origin after travelling through S, which is what proves store-and-forward rather than S inventing a copy.
Write this up as a strength, not a compromise. Two nodes that were never in contact exchanged data through a third that carried it. That is the defining property of a delay-tolerant network and it is more convincing evidence than three nodes syncing on one desk. Say in the report that the adapter shortage forced the stronger test.

E4. Partition and heal, with two nodes

The original plan called for isolating one of three nodes. With two adapters, unplugging one adapter IS the partition, and the test still demonstrates what matters.

  1. A and S on the mesh, both with adapters, synced and quiet.
  2. Unplug S's adapter. The partition has begun. Note the time.
  3. Create data on BOTH sides while they are separated: a victim message on each, and claim a message on one of them.
  4. Plug S's adapter back in and reboot S.
  5. Watch both nodes until every table matches. Record how many sync cycles it took.
EV-25c: the convergence check
| Table               | On A after heal | On S after heal | Match |
|---------------------|-----------------|-----------------|-------|
| messages            |                 |                 |       |
| personnel           |                 |                 |       |
| announcements       |                 |                 |       |
| gs_messages         |                 |                 |       |
| checkins            |                 |                 |       |
| personnel_locations |                 |                 |       |
| message_replies     |                 |                 |       |
| lora_events         |                 |                 |       |
All eight replicated tables, not just messages. Read the counts from curl -sk https://127.0.0.1:8443/health on each node. The claim you made during the partition must survive: a claimed message must not revert to unclaimed.

E5. Why the fallback test gets better

The fallback test needs a node whose Pi is dead. A dead Pi does not need a WiFi adapter. So with adapters in A and S and none in B, you can run the test exactly as designed, and you gain something:

Put the GCC on S, and let A be the node that physically hears B's LoRa beacon. The GCC then learns about the failure only because A heard it and the log replicated to S. That demonstrates the design decision behind the LoRa event log, which is that the node nearest a failure is not necessarily the node the operator is standing at. With three adapters you would probably have put the GCC on A and never shown it.

Mention this explicitly in the report. It is a concrete demonstration of why that table replicates while node health deliberately does not.

D

When a result disagrees with the design

It will, at least once. The instinct is to re-run until it agrees, or to quietly leave it out. Do neither.

The project already has the best possible example. The power chapter calculates a Battery A runtime and presents it as verified. Field testing found that the arrangement could not reliably power a node at all: the USB Wi-Fi adapter browned out and vanished from the bus, and sync kept logging SYNC_OK the whole time because a node with no peers has nothing to import. That result is worth more than the calculation it contradicts, because it is the only part of the power analysis that was tested against reality.

So when a number comes out wrong:

  1. Repeat it three times to be sure it is real and not a one-off.
  2. Record the conditions in full. Most disagreements turn out to be a condition nobody wrote down.
  3. Report both: the predicted value, the measured value, and the difference.
  4. Say what it changes. A measurement that changes a design conclusion is the most valuable kind, and saying so is what separates a results chapter from a list of numbers.
A results chapter where every measurement confirms the design reads as a chapter where nothing was genuinely tested. One honest disagreement, properly investigated, does more for the report than ten confirmations.
