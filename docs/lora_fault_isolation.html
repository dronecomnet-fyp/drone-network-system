Rescue Mesh · LoRa fallback · 9 August 2026

Find The Broken Link
In One Pass

The fallback chain has six links and every one of them fails silently. This walks all six in order, in about fifteen minutes, and ends knowing exactly which one is broken. No more one check at a time.

Time about 15 minutes Needs both nodes, both modules reflashed Ends with a named broken link
1 reflash→ 2 A can hear→ 3 B transmits→ 4 A receives→ 5 stored→ 6 shown
What is already proven, so we do not test it again. DRONE_B's module enters fallback and transmits: it reported beacon_sent n=12 then n=13, exactly 30 s apart, 158 bytes each. Links 1 and 3 below are known good on that module. The untested link is whether DRONE_A's radio is listening at all, and until this build there was no way to ask it.

The six links

  1. 0Reflash both, first
  2. 1Is A's radio armed?
  3. 2Is B transmitting?
  4. 3Does A hear B?
  5. 4Is it stored?
  6. 5Does the tab show it?
  7. 6Verdict table

Part one · Prepare

00

Reflash both modules first

Nothing below is trustworthy on old firmware. This build adds three things that exist purely to end this hunt: staged startup, a non-blocking serial write, and a receiver that reports whether it is armed.

laptop, once per module
$ cd ~/rescue-mesh && git pull
$ cd firmware/aux1
$ pio run -t upload
# press RESET on the module afterwards

# If upload fails with "Write timeout": press RESET and retry.
# Still failing: hold BOOT, tap RESET, release BOOT, retry.

Then put both modules back on their Pis and make sure both bridges are running:

on each node
$ sudo systemctl restart rescue-mesh-auxbridge
$ sleep 8
$ grep -a "AUX_STAGE\|AUX_BOOT" ~/rescue-mesh/backend/audit.log | tail -8
Expected on BOTH nodes
AUX_STAGE | at=alive | ms=...
AUX_STAGE | at=nvs | ...
AUX_STAGE | at=i2c | ...
AUX_STAGE | at=lora | ...
AUX_STAGE | at=ble | ...
AUX_BOOT  | node=DRONE_A | lora=OK | ina3221=OK | batt_a=... | batt_b=...
If the stages stop before AUX_BOOT, the last stage printed is the peripheral that hung. If lora=FAILED, stop here: that node is deaf and mute, and section 1 explains what to do.

Part two · Walk the chain

01

Is DRONE_A's radio armed?

This is the link that has never been checked, and the most likely culprit. Until this build the receiver had no way to say "I am listening"; it just sat there and a working radio looked exactly like a dead one.

The module now reports every 30 seconds. On DRONE_A:

on DRONE_A
$ grep -a LORA_STATUS ~/rescue-mesh/backend/audit.log | tail -3
$ curl -sk https://127.0.0.1:8443/health | grep -o '"aux_lora[^,]*'
How to read it
LORA_STATUS armed
The radio is up and listening. Good, go to section 2.
LORA_STATUS radio DOWN
Found it. A cannot hear anything. Fix below.
No LORA_STATUS at all
Old firmware, or the module is not talking to the Pi. Redo section 0.
If A's radio is down

The RFM95 did not initialise, so this node can neither hear a beacon nor raise one. Check the SPI wiring: MOSI, MISO, SCK, CS and RESET.

Check MISO especially. It had to be moved off the originally planned pin during bring-up because that pin never worked (CHANGES item 10). If this module was built or rewired later, confirm it matches the current pin map in firmware/aux1/src/main.cpp.

02

Is DRONE_B transmitting?

Already proven once, but reconfirm after reflashing. Put B's module into fallback by stopping its bridge, which is exactly what a dead Pi looks like to the module:

on DRONE_B
$ sudo systemctl stop rescue-mesh-auxbridge
$ cd ~/rescue-mesh
$ backend/.venv/bin/python tools/aux_raw_monitor.py
Expected within about 75 seconds
{"type":"fallback_enter"}
{"type":"beacon_sent","n":1,"len":158}
   ... every 30 s ...
15 s of missed heartbeats to enter fallback, or 60 s if the module rebooted when you touched it. Leave this running for the next section: B must keep beaconing while you check A.
Do not reboot B in the 90 seconds before this. A clean shutdown tells the module the silence is expected and it suppresses fallback for that long. Stopping the bridge, as above, does send that notice, so if you see no fallback_enter within 90 s that is why: wait it out.
03

Does A hear B?

While B is still beaconing, on DRONE_A. A new beacon lands every 30 seconds, so watch it live rather than grepping history:

on DRONE_A, leave running 90 s
$ tail -f ~/rescue-mesh/backend/audit.log \
    | grep --line-buffered -a "FALLBACK_BEACON\|LORA_STATUS\|LORA_RX"
Four possible outcomes, all of them conclusive
FALLBACK_BEACON appears
The whole radio path works. Go to section 4.
LORA_STATUS rx_total RISING, no beacon
A is hearing radio traffic but not B's beacons. Frequency or format mismatch: are both modules on the same firmware?
LORA_STATUS armed, rx_total STAYS 0
A is listening and hears nothing at all. This is range or antenna. Put the two modules a metre apart and repeat.
LORA_STATUS radio DOWN
Back to section 1.
Before blaming range, remember the transmit power

LoRa transmit power is deliberately pinned to the library minimum pending TRCSL confirmation for 915 MHz. Range is therefore very short by design. For this test the two modules should be on the same bench, about a metre apart. Testing at across-the- building distances proves nothing and has probably already cost you time.

04

Is it stored?

A beacon in the log still has to reach the database the Degraded tab reads.

on DRONE_A
$ sqlite3 ~/rescue-mesh/backend/drone_mesh.db \
    "select received_at, about_node, rssi from lora_events order by received_at desc limit 5;"
Reading it
Recent rows
Stored correctly. Go to section 5.
Log has beacons, table is empty
A real bug between the bridge and the database. Check for LORA_EVENT_LOG_FAIL in the log and report it.
Only rows older than 5 August
Those predate this table. They are in the audit log and node_health only, and cannot appear in the tab. Not a bug.
05

Does the tab show it?

Join the GCC to DRONE_A, the node that heard the beacon, and open the Degraded tab.

Two things that make a correct system look broken here. The degraded list only shows a node while beacons are RECENT, within 120 seconds, so if B has been powered back up it correctly disappears. And if the GCC is joined to a node that did not hear the beacon, it only knows through sync, which takes up to 30 seconds more.

Expected: DRONE_B listed, with beacon age, signal strength, which node heard it, its battery, and the last victim message it was carrying. Its map marker blinks.

My honest expectation. Given B transmits and A has never been asked whether it is listening, the most likely answer is section 1: A's radio never initialised. The second most likely is section 3 with rx_total at zero, which is range, because transmit power is pinned to minimum and you have probably not had the modules side by side.
