Rescue Mesh · bug-fix rollout · 2026-07-28

Rolling out the DEGRADED,
peer-info and GCC fixes

Four field bugs are fixed: a healthy drone stuck showing as DEGRADED, peers that showed only a last-seen time, a GCC that never noticed internet, and garbled flight controller messages. This is what to do to the kit you already have running. Nothing is reformatted, nothing is reinstalled, and no data is lost.

Touches all three Pis + both aux modules (A and B) Time about 20 minutes total Drive from Windows (SSH + PlatformIO)
pull + restart each Pi→ reflash both aux→ stale alert clears itself→ peers show position + battery
The short answer on "do I need to format or reflash?"

No formatting. No SD card reimaging. No flash erase. No re-provisioning.

The Pis take a git pull and a service restart. The aux modules take an ordinary pio run -t upload, which writes only the app partition and leaves NVS alone, so each module keeps its DRONE_A / DRONE_B identity and its cached last message. You never run erase_flash, and you never re-run setup_node.sh or make_fleet_ca.sh.

You also do not need to touch the database. The stale DEGRADED row on DRONE_A is left exactly where it is: the new code stops trusting it rather than deleting it, so it ages out on its own. No SQL, at all.

00

What broke, in one minute

The false DEGRADED alert had two causes, and both are fixed.

  • The aux module never recovered. It declares the Pi dead after 15 seconds of silence. Restarting rescue-mesh-auxbridge can take longer than that, so the module dropped into fallback, and fallback was one-way until a power cycle. It then beaconed over LoRa every 30 s forever and kept BLE switched off, so the drone also went invisible to the emergency app. That is almost certainly what happened to DRONE_B during the last update.
  • The GCC never expired the alert. The node stored a "degraded" flag and nothing anywhere ever cleared it, so one beacon heard once marked that drone down permanently.

Peers had no position because the mesh beacon deliberately carries only identity and counters, never GPS. Nodes now fetch each other's health over the sync link instead, so peers arrive with position, battery and their own data age.

Want the immediate workaround before you update anything? Power-cycle DRONE_B's aux module. That alone stops the false beacons today. The update below is what stops it happening again.
01

Update the three Pis

Identical on each node, in turn: DRONE_A, then DRONE_B, then DRONE_S. Leave the others running while you do one.

each Pi in turnA, B, S
$ cd ~/rescue-mesh
$ git pull
$ sudo systemctl restart rescue-mesh-api rescue-mesh-sync rescue-mesh-auxbridge

On DRONE_S only, also restart the MAVLink gateway. Do it with the flight controller disarmed and props off, since it briefly drops the control link:

drone-s shellDRONE_S
$ sudo systemctl restart rescue-mesh-mavgw
Expect a brief false alert while you do this. Restarting the aux bridge is exactly the thing that trips the old firmware into fallback. On the nodes you have not reflashed yet, that is still possible. It clears by itself once stage 2 is done, and after this update it stops being permanent even if it happens.
02

Reflash aux modules A and B

This is the real fix for the false alert, so do not skip it. DRONE_S has no aux module, so there are only two to do.

Plug module A into the laptop over USB. From the repo:

PowerShell · firmware\aux1LAPTOP
PS> cd firmware\aux1
PS> git pull
PS> pio run                # build only, catches errors first
PS> pio run -t upload      # then flash. repeat for module B
Do NOT erase the flash

pio run -t upload replaces only the program. The module's identity (DRONE_A or DRONE_B) lives in NVS and survives, so there is nothing to re-provision.

pio run -t erase or esptool erase_flash would wipe that identity and the module would come back as UNSET, beaconing under the wrong name. If it ever happens, fix it with python tools\aux_sim.py --port COMx then n DRONE_A.

Same binary for both modules; there is nothing to edit between them.

03

Gate — the false alert is gone

Open the GCC on RESCUE_A and look at Live Ops and the Map. The red "drone on LoRa fallback" banner for DRONE_B should be gone.

drone-a shellDRONE_A
$ curl -sk https://10.42.0.1:8443/health | python3 -m json.tool | grep -A6 degraded
Expected
"degraded_nodes": []

Two independent reasons it clears, so you do not have to wait for both: DRONE_B is an alive DTN peer (its signed mesh beacon proves its Pi is up, which outranks any LoRa claim), and the old claim is now older than the 120 s expiry. The stale database row is still there and that is fine — the node simply stops trusting it. Nothing to clean up.

Stop here

Confirm degraded_nodes is empty while DRONE_B is powered and healthy. If a node is genuinely down it should still appear, which stage 5 checks.

04

Gate — peers show position and battery

Allow one sync cycle (about 30 s) after the restarts, then on DRONE_A:

drone-a shellDRONE_A
$ curl -sk https://10.42.0.1:8443/health | python3 -m json.tool | grep -A14 peers
Expected: each peer now carries health, not just a timestamp
"peers": [
    { "node_id": "DRONE_B", "ip": "10.99.0.2",
      "last_seen": "...",         <- its mesh beacon
      "health_ts": "...",         <- when WE last fetched its health
      "lat": 6.92..., "lon": 79.86..., "gps_fix": 1,
      "bat_a_v": 7.8, "bat_b_v": 4.05, "clock_source": "gps" }
]

In the GCC's Nodes tab this fills the new Position, Battery A, Battery B and Info age columns. Beacon and Info age are separate on purpose: a peer can be beaconing right now while its cached position is minutes old, and the display must not pretend otherwise.

Stop here

Confirm at least one peer shows a position and an info age. "health_ts": null with everything blank means that peer has not been updated yet: finish stage 1 on it. A node with no GPS fix indoors correctly shows "no fix" rather than a made-up position.

05

Prove the recovery actually works

Worth doing once, because it is the behaviour that was broken and it is a good thing to be able to demonstrate. On DRONE_B:

drone-b shellDRONE_B
$ sudo systemctl stop rescue-mesh-auxbridge
$ sleep 30                                  # module enters fallback
$ sudo systemctl start rescue-mesh-auxbridge
$ journalctl -u rescue-mesh-auxbridge -n 20
  1. While the bridge is stopped, DRONE_A should show DRONE_B as degraded. That is correct: from A's point of view B's Pi really did stop talking.
  2. Within about 15 s of restarting it (3 pings at 5 s apart) the module leaves fallback on its own, stops the LoRa beacons and switches BLE back on.
  3. DRONE_A's alert clears by itself, no restart and no database edit.
Old behaviour, for contrast: step 2 never happened. The module stayed in fallback beaconing until someone unplugged it, and step 3 never happened either because the flag had no expiry. Full procedure in firmware/aux1/TESTS.md test 3b.
06

Rebuild the GCC

Several of these fixes are in the GCC itself, so the ground laptop needs a fresh build. New in this build: the peer Position and Battery columns, an internet indicator, and correctly joined flight controller messages.

PowerShell · repo rootLAPTOP
PS> cd gcc_app
PS> git pull
PS> flutter build windows
The phone apps do NOT need rebuilding for this fix. Nothing changed in them. Keep the phone-apps-v2 APKs you already have.
Check the new internet indicator
bottom of the navigation rail, under the node badge

Two rows now, because they are different questions. The top one is the drone node; the new bottom one is real internet, and you can click it to re-check immediately. On your home Wi-Fi it should read internet within a few seconds. Joined to a drone AP it should read no internet (portal), which is the correct answer in the field, not a fault. It checks itself every 30 s, so walking back into range updates it without you doing anything.

Why it never worked before: there was no internet detection code in the GCC at all. It only ever found out by failing a request, so joining a Wi-Fi with internet changed nothing you could see. It uses a captive-portal style probe (a URL that answers "204 No Content") rather than a ping, because ICMP ping needs raw sockets that a desktop app does not have.

Troubleshooting

SymptomTry this
A drone STILL shows degraded after the updateCheck it is actually up: is it listed under peers? If it is a live peer the alert cannot persist, so a lasting alert means the mesh link to it is down, which is a real fault worth investigating rather than a display bug. If it is not a peer and not really down, its aux module is probably still on old firmware and beaconing: finish stage 2 on it, or power-cycle that module.
Peers still show no positionThe peer itself must be updated, not just the node you are looking at: the position comes from that peer's own /health. Check for PEER_HEALTH_FAIL in ~/rescue-mesh/backend/audit.log, and allow one 30 s sync cycle.
An aux module now reports as UNSETIts flash was erased at some point. Reprovision: python tools\aux_sim.py --port COMx, then n DRONE_A or n DRONE_B, and check the ack.
A drone keeps flipping in and out of fallbackRecovery deliberately needs 3 consecutive pings, so genuine flapping means the Pi itself is unstable. Check journalctl -u rescue-mesh-auxbridge for the bridge restarting in a loop, and check power.
Flight controller messages look like fragments, e.g. a lone "(xy diff:110 > 100)"Fixed in this GCC build: long ArduPilot messages are split across several MAVLink packets and the old build printed each piece as its own line. Rebuild the GCC (stage 6). The underlying PreArm messages are real FC configuration issues and still need fixing on the flight controller.
The emergency app cannot see a drone over BluetoothBLE is switched off while a module is in fallback. If the drone is healthy, that module is stuck in old-firmware fallback: reflash (stage 2) or power-cycle it.
