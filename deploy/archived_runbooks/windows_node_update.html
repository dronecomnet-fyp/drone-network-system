Read this first — what this update is, and is not

Almost all the change this cycle was in the apps (GCC and the rescue app). On the nodes the backend code did not change this cycle, so the node side is a plain git pull + service restart to make sure all three Pis are on the current code that the new apps talk to (rescuer locations, checkins, health). There is no manual database migration: the service creates any missing table on start (CREATE TABLE IF NOT EXISTS), so no SQL and no data loss.

The aux modules do need reflashing this time (Stage 3): Battery B is wired to INA3221 channel 2, and both battery channels are now read as bidirectional, so a pack on charge reports a negative current instead of a wrong one. Check the sign on the bench as part of that stage.

DRONE_S is not optional here. It runs the same backend and is a sync peer of both A and B (10.99.0.3), so if it stays on old code the new personnel_locations table never converges with it: A and B will log SYNC_FAIL | peer=DRONE_S | table=personnel_locations every cycle while every other table keeps working. Update all three. DRONE_S has no aux module, so the firmware stage does not apply to it.

This is the update runbook. For building a Pi from a blank card, the fresh-setup runbook is still deploy/windows_mesh_bringup.html; the secrets rule there (copy DRONE_A's deploy/secrets/, never run make_fleet_ca.sh on B) is unchanged and untouched by this update.

Before you start

  • Power all three Pis (A, B and S), keep them within a couple of metres so the mesh cell stays up during and after the update.
  • Each Pi reachable from the Windows laptop over Ethernet or the same LAN: ssh drone@drone-a.local, drone-b.local, drone-s.local.
  • For stage 4 (aux firmware, A and B only): the Windows laptop with PlatformIO (pio) and a USB lead to the module. Skip if you are not touching Battery B yet.
Order matters a little: update DRONE_A first, confirm it is healthy, then DRONE_B, then DRONE_S. Doing one at a time keeps a known-good node up while you work on the other.
01

Update each Pi: pull, restart, verify

Run these on DRONE_A first, confirm the gate at the bottom, then repeat the exact same block on DRONE_B, then on DRONE_S. Nothing here is node-specific: all three run the same backend. DRONE_S needs one extra service restart, covered in stage 3.

drone-a shell (then drone-b, then drone-s)DRONE_A
$ cd ~/rescue-mesh
$ git pull
$ sudo systemctl restart rescue-mesh-api rescue-mesh-sync rescue-portal rescue-mesh-auxbridge
$ curl -sk https://10.42.0.1:8443/health | python3 -m json.tool

If git pull says Already up to date, that is fine: it means this node already carried the current code (for example you ran the M7d update earlier). The restart is still worth doing so the running process matches the files.

Expected /health highlights (per node)
"node_id": "DRONE_A",              (and "DRONE_B" on the other)
"aux": "present",
"gps": { ... "fix": 1 near a window ... },
"table_counts": { ... "personnel_locations": 0, "checkins": 0 ... }

The one field that proves this update landed is personnel_locations under table_counts. If it is missing, the node is still on older code — see troubleshooting. A quick one-liner: curl -sk https://10.42.0.1:8443/health | grep personnel_locations.

Stop here (per node)

On this node, confirm the four services came back active, /health shows the right node_id with aux present, and personnel_locations appears in table_counts. Only then move to the other Pi.

02

Gate — the fleet still converges

All three nodes updated. Prove the mesh is unbroken and the new rescuer-location table replicates like every other table. First, DRONE_A should see BOTH other nodes as peers:

drone-a shellDRONE_A
$ ping -c 2 10.99.0.2                                  # B on the mesh
$ ping -c 2 10.99.0.3                                  # S on the mesh
$ curl -sk https://10.42.0.1:8443/health | python3 -m json.tool | grep -A4 peers
Expected
"peers": [ { "node_id": "DRONE_B", "ip": "10.99.0.2", "last_seen": "..." },
           { "node_id": "DRONE_S", "ip": "10.99.0.3", "last_seen": "..." } ]

If DRONE_S is missing here, it is either powered down or not on the IBSS cell. A peer that is present but stale is the more telling case: check A's audit log for SYNC_FAIL | peer=DRONE_S lines naming a table, which is the signature of a node still on old code.

Now the real proof for the new feature: a rescuer location created at one node reaches the other. Easiest with a phone at DRONE_B:

  1. Phone joins RESCUE_B, opens the rescue app, logs in with a PIN.
  2. Settings → Share my location ON. Wait about 90 seconds (one heartbeat), then a further ~40 s for the mesh pull.

Then read it back from DRONE_A (the HQ break-glass key is fine for this GET):

drone-a shellDRONE_A
$ HQ=$(grep HQ_API_KEY ~/rescue-mesh/deploy/secrets/fleet_secrets.env | cut -d= -f2)
$ curl -sk -H "X-API-Key: $HQ" https://10.42.0.1:8443/personnel-locations | python3 -m json.tool
Stop here — the M7d proof

If the rescuer who logged in at B shows up in /personnel-locations read from A, the new location table replicates across the mesh exactly like messages and personnel do (newest-wins, signature-checked). No phone to hand? The peer check plus the personnel_locations count in table_counts is enough to show the code deployed; the sync path is the same proven one the gs-uplink test already exercises.

03

DRONE_S: the system drone extras

DRONE_S is a full mesh node like the others (same image, same backend, same sync), so stage 1 applies to it unchanged. What differs is what hangs off it. It is the only node with a flight controller, and the only node with no aux module at all: AUX_SERIAL is empty in deploy/nodes/drone_s.conf, so there is no INA3221, no LoRa, and no separate GPS. Its position and battery come from the flight controller over MAVLink instead.

So after the stage 1 pull, restart the gateway too:

drone-s shellDRONE_S
$ sudo systemctl restart rescue-mesh-mavgw
$ systemctl is-active rescue-mesh-mavgw     # active
$ curl -sk https://10.42.0.1:8443/health | python3 -m json.tool
Restarting the gateway drops the live control link

rescue-mesh-mavgw is the transparent serial-to-UDP bridge the GCC talks to. Restarting it cuts the MAVLink link for a few seconds, so do it with the flight controller disarmed and props off, never while the GCC is mid-command. That matches the standing props-off bench policy, which this update does not change.

Expected /health on DRONE_S, which looks different on purpose
"node_id": "DRONE_S",
"aux": "absent",              <- CORRECT here, not a fault
"gps": { ... from the flight controller, via the gateway tap ... },
"table_counts": { ... "personnel_locations": 0 ... }

"aux": "absent" is the expected, healthy reading on DRONE_S: there is no module to find. Do not chase it. Battery A/B will also be empty for the same reason, which is exactly why this cycle added the system-drone battery and GPS card to the GCC, sourced from live MAVLink rather than from /health.

One honest consequence of having no aux: DRONE_S cannot send a LoRa fallback beacon. If its Pi loses power, the other nodes hear nothing from it, so it goes quiet rather than appearing as a red DEGRADED alert the way A or B would. That is a property of the hardware, not a bug in the alerting, and it is worth stating when demonstrating the fallback feature.
04

Aux firmware (DRONE_A and DRONE_B only)

DRONE_S has no aux module, so skip this stage for it entirely. For A and B: wire Battery B to INA3221 channel 2 (Battery A stays on channel 1), then reflash both modules. The firmware change (CHANGES.md item 30) is that both channels are now read as bidirectional: the shunt register is signed, so a pack being charged reports a negative current rather than a nonsense one.

The convention, fleet-wide

Positive = discharging (the pack is supplying the load). Negative = charging (current flowing into the pack). Near zero = idle; anything under 5 mA is called idle, because one ADC count is 0.4 mA and a resting line jitters either side of zero.

This matters most for Battery B, which design v3 has charging from the Pi's USB during normal operation and taking over in fallback. So on a healthy node, Battery B reading negative is the system working correctly, not a fault.

Flash each module from Windows with it on USB. The node identity lives in flash and survives a reflash, so DRONE_A stays DRONE_A:

PowerShell · firmware\aux1LAPTOP
PS> git pull
PS> pio run -t upload           # module A on COMx; repeat for module B
After flashing: confirm on the Pi
$ curl -sk https://10.42.0.1:8443/health | python3 -m json.tool | grep -A6 battery

Both "b_v" and "b_ma" should now carry numbers (under item 26's withdrawn design b_ma was always null). The fallback beacon layout is unchanged, and the Pi bridge parses with float(), so a negative value flows end to end with no Pi-side change. If unsure a module kept its identity, run python tools\aux_sim.py --port COMx then n DRONE_A (or DRONE_B) and check the ack.

Stop here — check the sign per channel

With the Pi powered over USB, Battery B should read negative (charging) or near zero (full), and Battery A should read positive under load. If a channel reads positive while it is plainly on charge, that channel's shunt is wired the other way round: set BATT_A_SHUNT_INVERT or BATT_B_SHUNT_INVERT to true in src/main.cpp and reflash. Do not re-solder for this. If Battery B reads a steady positive draw while the Pi is alive, it is not charging at all, which is the open power question in file 03 — log it in docs/test_log.md.

Range: the channel measures +/-1638 mA with the 100 milliohm shunts and clips at that rail rather than wrapping, so a very large charge or load current is under-reported but never reports the wrong direction. Full procedure in firmware/aux1/TESTS.md tests 1 and 6.
05

Rebuild the apps + prepare the Field Share bundle

The nodes now serve the data; these are the consumer-side builds that show it. On the Windows laptop:

PowerShell · repo rootLAPTOP
PS> cd gcc_app     & flutter build windows        # Live Ops + Map alerts, Field Share tab
PS> cd ..\rescue_app & flutter build apk --release  # fallback banner + ops map tab
  • GCC: reinstall the new Windows build on the ground laptop. New this cycle: the system-drone live battery/GPS card, the LoRa-fallback alert on Live Ops and the Map, and the Field Share tab.
  • Rescue app: you do not have to build this yourself. The signed APK is published on the repo's GitHub releases page as phone-apps-v2 (rescue-app-v2.1.apk), together with emergency-app-v0.1.1.apk. Download those, drop them in the Field Share folder, and hand them out. Build locally only if you have changed the app since that release.

Field Share bundle (task E): put the two release APKs and your offline region maps into one folder, then serve them from the GCC Field Share tab over a local router or the laptop hotspot. Full operator steps are in docs/FIELD_SHARE.md.

APK version check: the runbook's stage 2 gate needs Settings → Share my location, which only exists in rescue-app-v2.1.apk or newer. If that toggle is missing on the phone, it is running the older phone-apps-v1 build; install v2.1 over it (same signing key, no uninstall needed).
macOS demo note: Field Share also runs under flutter run -d macos (the dev build already carries the network-server entitlement). The Windows build needs no entitlement.

Troubleshooting

SymptomTry this
personnel_locations missing from /health table_countsThe node is still on old code. Confirm the pull landed: git -C ~/rescue-mesh log -1 --oneline should match origin. If it does, restart the services again; the table is created on start, so a clean restart on current code makes it appear.
Rescue app map shows victims and drones but no teammatesEither this node predates the update (check the row above), or the other rescuers have Share my location off. Confirm /personnel-locations returns entries; heartbeats are foreground-only and every ~90 s, so allow a minute.
/personnel-locations returns 403 with the HQ keyOnly the GET is HQ-allowed; POSTing a location needs a rescuer session token (identity comes from the token, by design). Read with the HQ key, write from the app.
A battery current has the wrong sign (charging shows as a draw, or the reverse)That channel's shunt is wired with IN+ and IN- swapped. Set BATT_A_SHUNT_INVERT or BATT_B_SHUNT_INVERT to true in firmware/aux1/src/main.cpp and reflash (Stage 3). No re-soldering needed.
Battery B shows a steady positive draw while the Pi is poweredIt is not charging from the Pi USB, which design v3 assumes it does. Check the USB/charge path before any long unattended run, and log the finding (file 03 power note, still open).
A and B log SYNC_FAIL | peer=DRONE_S | table=personnel_locationsDRONE_S is still on old code and has no such table or sync route. Run stage 1 on it. Failures are isolated per table, so every other dataset keeps syncing meanwhile, which is why this can go unnoticed: check the audit log rather than assuming silence means health.
DRONE_S /health says "aux": "absent"Expected and correct: DRONE_S has no aux module (AUX_SERIAL is empty in its conf). Its GPS and battery come from the flight controller through rescue-mesh-mavgw, and the GCC shows them on the system-drone card, not in the aux battery fields.
GCC loses the drone link after updating DRONE_Ssudo systemctl restart rescue-mesh-mavgw, then confirm systemctl is-active rescue-mesh-mavgw. The GCC reconnects on its own once the UDP bridge is back; the heartbeat gate in the Drone tab is what tells you it is live again.
Peer disappears / sync stops after the restartNot caused by this update (no secrets or network change here). Same checks as bring-up: iw dev wlan1 info shows type IBSS on both, ping 10.99.0.2 works, and tail ~/rescue-mesh/backend/audit.log has no SYNC_REJECT.
Fallback alert never appears in the appsThe alert is driven by a DEGRADED node in /health, which only happens when a Pi is actually down and its aux is heard over LoRa. To rehearse it, power a Pi off and watch a neighbour's degraded_nodes populate.
