01

Update the three Pis

Same on each in turn: DRONE_A, DRONE_B, then DRONE_S.

each Pi in turnA, B, S
$ cd ~/rescue-mesh
$ git pull
$ sudo systemctl restart rescue-mesh-api rescue-mesh-sync rescue-portal rescue-mesh-auxbridge

On DRONE_S only, also restart the gateway, with the flight controller disarmed and props off:

drone-s shellDRONE_S
$ sudo systemctl restart rescue-mesh-mavgw
Expect a brief false DEGRADED alert during this. Restarting the aux bridge is exactly what trips the OLD firmware into permanent fallback. It stops being permanent once stage 2 is done.
02

Reflash aux modules A and B

This is the real fix for the stuck DEGRADED alert. DRONE_S has no aux module, so there are only two.

PowerShell · firmware\aux1LAPTOP
PS> cd firmware\aux1
PS> git pull
PS> pio run                # build only, catches errors first
PS> pio run -t upload      # then flash. repeat for module B
Never erase the flash

pio run -t upload replaces only the program; the module keeps its DRONE_A or DRONE_B identity from NVS. pio run -t erase or esptool erase_flash would wipe that and the module returns as UNSET. If that happens: python tools\aux_sim.py --port COMx then n DRONE_A.

Same binary for both. Nothing to edit between them.

03

Rebuild the GCC

PowerShell · repo rootLAPTOP
PS> cd gcc_app
PS> git pull
PS> flutter build windows

New in this build: peer Position and Battery columns, an internet indicator under the node badge, and flight controller messages joined into whole sentences.

The internet indicator, and how to read it
bottom of the navigation rail, two rows now

Top row is the drone node. New bottom row is real internet, clickable to re-check. On home Wi-Fi it should say internet within a few seconds. On a drone AP it should say no internet (portal), which is the CORRECT answer in the field and not a fault. It never worked before because the GCC had no detection code at all; it now uses a captive-portal probe, since a real ICMP ping needs privileges a desktop app does not have.

04

Rebuild and publish the APKs

The emergency app changed (notification spam fix), so it needs a new release. Bump the version first, then build, then publish, per docs/RELEASES.md.

PowerShell · repo rootLAPTOP
PS> cd emergency_app ; flutter test ; flutter build apk --release
PS> gh release create phone-apps-v3 --title "..." --notes "..." ^
       emergency-app-vX.Y.Z.apk rescue-app-vX.Y.apk
Build on the SAME machine as last time. Release builds are signed with the per-machine debug keystore, so an APK built elsewhere will not install over the existing app. Check with apksigner verify --print-certs before publishing.
05

Check the new victim portal

Join RESCUE_A from a phone and open the portal. This is the change testers asked for, so it is worth looking at properly.

  1. You should see large tappable options (I am trapped, Someone is injured, ...) with the urgent ones first. No typing is required anywhere.
  2. The phone should ask for location straight away, without you pressing anything. Allow it: the box turns green and states the accuracy.
  3. Deny it instead, and the page should tell you to describe a landmark rather than just failing.
  4. Tap one option and press SEND. The confirmation should say the drone HAS your message and that carrying it back can take a while.
Stop here

Confirm you can send a usable message without typing a single character, and that the message arrives in the GCC Live Feed with the option text as its content. If the options look generic, that is correct for now: every node serves the stock list until the GCC push UI is built.

Gates before you call it done

drone-a shellDRONE_A
$ curl -sk https://10.42.0.1:8443/health | python3 -m json.tool | grep -A8 -E "peers|degraded|mission_config"
Expected
"mission_config": { "version": 0, "source": "stock", ... }
"degraded_nodes": []
"peers": [ { "node_id": "DRONE_B", "lat": ..., "bat_a_v": ..., "health_ts": ... } ]

"source": "stock" is expected until the GCC can push. degraded_nodes empty while B is healthy is the stuck-alert fix. Peers carrying lat and battery is the peer-info fix.

  • Emergency app: stand in range of a drone for a few minutes. You should get one notification, not a stream.
  • GCC: internet row reads internet on home Wi-Fi.
  • GCC Drone tab: flight controller messages read as whole sentences.
07

Troubleshooting

SymptomTry this
Portal still shows the old typing formrescue-portal did not restart, or the pull did not land. Check git -C ~/rescue-mesh log -1 --oneline, then restart it. Hard-refresh the phone browser: captive portal pages cache aggressively.
Portal options look generic for the disasterCorrect for now. Every node serves the stock need-based list until the GCC push UI is built. /health will say "source": "stock".
A drone still shows DEGRADEDIf it is listed under peers the alert cannot persist, so a lasting alert means the mesh link to it is genuinely down. If it is not a peer and not really down, its aux is still on old firmware: finish stage 2 or power-cycle that module.
Peers show no positionThe PEER must be updated, not just the node you are looking at. Check for PEER_HEALTH_FAIL in backend/audit.log and allow one 30 s sync cycle.
GCC internet row says no internet on a Wi-Fi that worksCorporate or campus networks sometimes block the probe endpoints. Click the row to re-check. If a browser on the same laptop reaches the internet but the GCC does not, tell me and I will add a configurable probe URL.
Emergency APK will not install over the old oneIt was built on a different machine, so the debug signing key differs. Either build on the original machine or uninstall the old app first (which loses its local data).
